The **Single Responsibility Principle (SRP)** is the first and one of the most crucial principles of the SOLID design principles in software engineering. Introduced by Robert C. Martin (Uncle Bob), SRP states:

> **A class should have only one reason to change.**

This principle is foundational for writing maintainable, testable, and clean code. In this article, we’ll dive deep into SRP, its importance, and how to apply it in real-world TypeScript projects.

## 🚀 What is the Single Responsibility Principle?

The SRP emphasizes **separation of concerns**. Every module, class, or function should have **one and only one job**. If it has more than one responsibility, changes in one responsibility might impact the other, making the code fragile and harder to maintain.

### ❌ Example of a Class Violating SRP

Let’s look at an example where SRP is violated:

<CodeBlock title="Typescript" raw={`class UserManager {
  createUser(name: string, email: string) {
    // logic to create a user
  }

saveToDatabase(user: any) {
// logic to save user to database
}

sendWelcomeEmail(user: any) {
// logic to send email
}
}`}>

```ts
class UserManager {
  createUser(name: string, email: string) {
    // logic to create a user
  }

  saveToDatabase(user: any) {
    // logic to save user to database
  }

  sendWelcomeEmail(user: any) {
    // logic to send email
  }
}
```

</CodeBlock>

In this example, UserManager is doing three things: 1. Managing user creation logic 2. Handling database operations 3. Sending emails

These are three separate responsibilities. If the email logic changes, the UserManager class will need to be updated. This tightly couples unrelated concerns.

✅ Applying SRP: Better Structure

We can refactor the above class by splitting responsibilities into separate classes:

```ts
class User {
  constructor(
    public name: string,
    public email: string,
  ) {}
}

class UserRepository {
  save(user: User) {
    // logic to save user to database
  }
}

class EmailService {
  sendWelcomeEmail(user: User) {
    // logic to send welcome email
  }
}

class UserService {
  constructor(
    private userRepository: UserRepository,
    private emailService: EmailService,
  ) {}

  createUser(name: string, email: string) {
    const user = new User(name, email);
    this.userRepository.save(user);
    this.emailService.sendWelcomeEmail(user);
  }
}
```

Now we have:
• User: Represents the domain model.
• UserRepository: Responsible only for data storage.
• EmailService: Handles email-related logic.
• UserService: Coordinates user creation but delegates other responsibilities.

💡 Benefits of Following SRP

By applying SRP, we gain several advantages:
• Better Maintainability: When a change occurs in the database logic, only UserRepository needs to change.
• Improved Testability: Each class can be tested independently with unit tests.
• Higher Readability: Smaller classes are easier to read and understand.
• More Flexibility: Easy to replace email service or database layer without affecting user logic.

🧪 Example Unit Tests

Here’s how easy it is to test individual responsibilities:

// Test EmailService
const emailService = new EmailService();
emailService.sendWelcomeEmail(new User("Jane", "jane@example.com"));

// Test UserRepository
const userRepository = new UserRepository();
userRepository.save(new User("John", "john@example.com"));

No need to deal with user creation or dependencies – each class is independent.

🧱 SRP Beyond Classes: Functions Too

SRP isn’t just for classes — it applies to functions as well. Avoid writing functions that do multiple things.

❌ Bad Example

```ts
function generateReport(data: any) {
  // gather data
  // format data
  // send report via email
}
```

✅ Good Example

```ts
function fetchData(): any {
  // logic to fetch data
}

function formatReport(data: any): string {
  // logic to format data
}

function sendReport(report: string) {
  // logic to send report
}
```

Each function now has a single responsibility.

🧠 Conclusion

The Single Responsibility Principle is a simple yet powerful concept. It encourages modular design, where each component has one clear purpose. By respecting SRP in your TypeScript code:
• You make your code cleaner,
• Your application becomes easier to test and extend,
• And your development process becomes more agile.

Always ask yourself:

“If I change X, will it affect unrelated parts of this class or function?”

If the answer is yes, consider applying SRP.
