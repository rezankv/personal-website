## Introduction

In the world of software development, writing code that “just works” is not enough. Applications that become increasingly complex, buggy, and difficult to maintain as they grow often suffer from poor design practices. One of the most important sets of principles that helps us write clean, scalable, and maintainable code is the SOLID principles.

SOLID is a collection of five principles introduced by <Link href="https://en.wikipedia.org/wiki/Robert_C._Martin" target="_blank">Robert C. Martin</Link>. These principles help us eliminate improper dependencies, make changes without breaking other parts of the system, and avoid unnecessary architectural complexity. Following these principles is especially valuable in long-term and team-based projects, making software development a more enjoyable and reliable experience.

In this “SOLID Simplified” series, we’ll learn these five principles together in a straightforward way.

## The Second SOLID Principle: Open/Closed Principle

This principle says:

> **Classes, modules, or functions should be open for extension but closed for modification.**

But what does that mean?

It means we should be able to **add new functionality without modifying existing code**. This is usually achieved through **inheritance** or **polymorphism**.

### Let’s look at an example:

❌ **Violating the OCP**

<CodeBlock title="Typescript" raw={`class SalaryCalculator {
  calculate(employee: { type: string; baseSalary: number }): number {
    if (employee.type === "developer") {
      return employee.baseSalary + 1000000;
    } else if (employee.type === "manager") {
      return employee.baseSalary + 5000000;
    } else {
      return employee.baseSalary;
    }
  }
}`}>

```ts
class SalaryCalculator {
  calculate(employee: { type: string; baseSalary: number }): number {
    if (employee.type === "developer") {
      return employee.baseSalary + 1000000;
    } else if (employee.type === "manager") {
      return employee.baseSalary + 5000000;
    } else {
      return employee.baseSalary;
    }
  }
}
```

</CodeBlock>

What’s the problem?

If you later want to add a new role (like “intern”), you’ll have to change the original class. That means the code is not closed to modification.

#### ✅ Proper OCP Implementation

Let’s restructure things so each role handles its own salary calculation:

<CodeBlock title="“Typescript”" raw={`interface Employee {
baseSalary: number;
calculateSalary(): number;
}

class Developer implements Employee {
constructor(public baseSalary: number) {}
calculateSalary(): number {
return this.baseSalary + 1000000;
}
}

class Manager implements Employee {
constructor(public baseSalary: number) {}
calculateSalary(): number {
return this.baseSalary + 5000000;
}
}

class Intern implements Employee {
constructor(public baseSalary: number) {}
calculateSalary(): number {
return this.baseSalary;
}
}

function printSalary(employee: Employee) {
console.log(“Salary:”, employee.calculateSalary());
}`}>

```ts
interface Employee {
  baseSalary: number;
  calculateSalary(): number;
}

class Developer implements Employee {
  constructor(public baseSalary: number) {}
  calculateSalary(): number {
    return this.baseSalary + 1000000;
  }
}

class Manager implements Employee {
  constructor(public baseSalary: number) {}
  calculateSalary(): number {
    return this.baseSalary + 5000000;
  }
}

class Intern implements Employee {
  constructor(public baseSalary: number) {}
  calculateSalary(): number {
    return this.baseSalary;
  }
}

function printSalary(employee: Employee) {
  console.log("Salary:", employee.calculateSalary());
}
```

</CodeBlock>

Now, if a new role is introduced, we just create a new class—no need to touch the existing ones.

#### Why is the Open/Closed Principle important?

- ✅ No risk of breaking existing logic
- ✅ Different teams can add new features independently
- ✅ Unit tests remain intact
- ✅ The system becomes more scalable

#### How do we apply this principle?

- Use interfaces or abstract classes to define common behavior
- Use dependency injection to pass in dependencies
- Extend functionality through inheritance or composition

#### ⚠️ Note

OCP doesn’t mean “always use inheritance.”
Sometimes, composition is a better choice depending on the context.

#### Summary

The Open/Closed Principle helps your code resist change while remaining extendable.
Remember: less modification = fewer bugs = lower cost.
